# SonarModule — the navigator's sonar console

The navigator's sonar console on the radar module. Read the [root AGENTS.md](../../../../AGENTS.md) first (game, rules, module map). Change this module's description here, not in the root file.

## Assembly
- `Features.SonarModule.Contracts` (layer 1; no references): `SonarModule/Contracts/`: `ISonarContactSource`, `SonarContact`, `SonarContactKind`, `ISonarCondition`, so a module adds its own sonar contacts or says whether the radar works without referencing the sonar.
- `Features.SonarModule.Data` (layer 1; references: SonarModule.Contracts, NetworkModel, Mirror, Zenject): the generated `SonarConsole` model with `SonarMark`, and the sonar's local models.
- `Features.SonarModule` (layer 6; references: SonarModule.Contracts, SonarModule.Data, Ship, Grab, Camera, CharacterMovable, Mvp, PlayerLife, FlightFieldModule.Contracts, GameCoreModule.Contracts, GameFlow, NetworkModel, Mirror, Zenject, Input, UnityEngine.UI, DebugModule.Contracts): the navigator's sonar console; its own module rather than more radar code in the ship module, because it needs the UI, the player's life and the field contracts the ship must not depend on, and the ship stays unaware of it.

## Key places
| What | Where |
|---|---|
| Sonar (navigator) | `Assets/Features/SonarModule/` (`Contracts`, `Data`, `Scripts`). The radar module (`RadarModule.asset`, slot `radar`) is a **console**: its slot view `RadarItemView` is a pedestal with a screen, and `ShipPlatform/RadarSocket/SonarConsole` (trigger box on the screen, layer 7) carries `SonarConsoleInteractable`. The console is active only while a module stands in the socket and the ship flies (`ShipRunPhase.IsFlight()`: Takeoff / Cruise / Landing), so at a station E on the module still takes it off. E sends the use command; the server (`SonarNavigatorSystem`, `SonarConsoleRule`) seats **one navigator by `PlayerKey`** in the synced Shared `SonarConsole` model (`NavigatorKey`; bridge `SonarConsoleSync` on `RadarSocket`, which also binds the console in `SonarConsoleBindingModel`) and opens the console on that player's peer (`TargetOpenConsole` -> `SonarScopeModel.Open`). `SonarWindowSystem` then opens the MVP `SonarWindow` (`SonarScopeView` / `SonarScopePresenter`, prefab `SonarModule/GameResources/Prefabs/SonarWindow`, Addressables `Windows`), blocks walking and aim (`PlayerControlBlockModel`) and frees the cursor; Esc, E or the Leave button close it, `SonarConsoleReachSystem` closes it when the player dies, walks farther than `ConsoleKeepOpenMeters` or the server gave the seat away; closing sends `CmdLeave`; the server also frees the seat on disconnect, distance or landing. **Ping game** (`SonarScopeSystem`, numbers in `SonarConfiguration_Default`, Addressables `Configurations`): Space or the Ping button (cooldown `PingCooldownSeconds`) takes the contacts within range from this peer's own data, a wave runs from the ship to the edge in `PingWaveSeconds` and lights each contact as it passes, an echo fades over `EchoFadeSeconds`; top view around the ship, nose up, `RangeRingCount` rings (`SonarScopeLayout`). The range is the ship's `SonarRange` stat (synced in `ShipStats`; the radar module adds 800 m, never below `MinRangeMeters`). The ping's sound is the view's `AudioSource` (no clip yet). **Contacts** come only through `ISonarContactSource` (Contracts), all bound in `SonarModuleInstaller` and read as one by `SonarContactService`: `RockSonarContactSource` (every large rock of `IPeerFieldRockQuery`, the published field on every peer, is a contact `rock:c:..` / `rock:d:..`; small rocks count per `DebrisCellMeters` world cell, `DebrisMinRocks` make one `debris:x:z` contact), `StationSonarContactSource` (`station`, the run's `TransitDestination`, in flight) and `TargetSonarContactSource` (every balloon of `IPeerFieldTargetQuery` is a `target:<index>` contact; a popped one is gone). A kind is a `SonarContactKind` asset (id, colour, icon, pixels, mark seconds, markable, shown on the edge beyond range: `SonarKind_Station` blue, `SonarKind_LargeRock` red, `SonarKind_Debris` orange, `SonarKind_Target` yellow), never a branch. **Marks:** a click on an echo -> `CmdMark` -> `SonarMarkSystem` with `SonarMarkRule` (`CreateMark` builds the mark; the sender is the navigator, the contact exists now and is markable, at most `MarkLimit` marks; marking a marked contact renews it) -> `SonarMark` (contact id, kind id, position over the object's top, `ExpiresAt` in network time) in the synced `Marks` list, so a late joiner gets the active marks; the server drops a mark when its time is up or its contact is gone (a broken rock). Every peer: `SonarMarkerSystem` lays the marks out on its screen (`SonarMarkerProjection`: over the object, else on the screen edge less `MarkerEdgeMarginPixels` with an arrow) into `SonarMarkerScreenModel`, and `SonarMarkersView` in `GameHudWindow` draws icon, glow, distance and arrow at a constant size. **Own station marker (debug):** the debug window's Ship → "Show station: off / on" (`SonarStationMarkerDebugSystem`, editor / development builds only; the button registers again with the new label) sets the local, unsynced `SonarStationMarkerModel`; while it is on and the ship flies, `SonarStationMarkerSource` hands `SonarMarkerSystem` the station from `IStationSonarContactSource` (`StationSonarContactSource`, the synced run's `TransitDestination`), laid out like a crew mark but only on this peer's screen, so a pilot playing solo sees where to fly. Off by default; off or at a station nothing is shown. **Broken radar:** `RadarSonarCondition` (`ISonarCondition`) asks `IShipModuleCondition` about the console's socket (`SonarConsoleSync._socket`, bound in `SonarConsoleBindingModel`): a broken radar still opens and pings, but its wave finds nothing and the window shows "NO SIGNAL: the radar needs repair" until a mechanic repairs it (with a tool in the hand the screen's collider offers the socket's repair, not the console). The old minimap (`ShipRadarService`, `ShipRadarScreen`, `ShipRadarCatalog`, the HUD radar) is gone |

## Known limits
- **The sonar reads the published field.** Its rock and balloon sources use the peer queries (`IPeerFieldRockQuery`,
  `IPeerFieldTargetQuery`) over the live field model, so a navigator on a client sees the same contacts as one on the
  host, but only once the field is published (about a second into the takeoff on a loop 9 field); the server's checks
  keep the generated field.
